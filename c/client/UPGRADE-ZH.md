# 客户端远程升级

在 Web 控制台把新版客户端安装包上传到网关，然后对单个节点或所有旧版本节点下发升级。
安装包保存在网关，客户端从**网关**下载，不需要访问 GitHub。

## 使用

1. 登录网关控制台，在「客户端升级」面板点「上传安装包」。
2. 选择平台（Windows / Linux / Android / macOS）、填写版本号（如 `2.0.2`）、选择文件。
3. 上传后，节点列表里版本较旧的在线节点会出现「升级到 2.0.2」按钮；也可以点
   「升级所有旧版本」一次性下发。

节点在线时立即执行；离线节点不会收到指令，下次上线后仍需再次下发（升级指令不排队）。

## 各平台的行为

| 平台 | 行为 | 是否需要人工确认 |
|---|---|---|
| Windows | 下载校验后，新版本从临时目录启动一个助手：等旧服务停止、替换 `C:\Program Files\fastp2p\fastp2p.exe`、再启动服务 | 否 |
| Linux | 下载校验后原地替换可执行文件并 `execv` 重新执行，进程号不变，systemd 不需要重启单元 | 否 |
| macOS | 同 Linux（launchd 不受影响） | 否 |
| Android | 下载校验后把 APK 交给系统安装器 | **是**，手机上必须点一次「安装」 |

## 安全模型

- 上传接口需要控制台登录凭据（JWT）。
- 下载接口需要网关的 16 位安装 Token，与客户端登录用的是同一个密钥。
- 客户端按网关下发的 SHA256 校验安装包，**校验不通过绝不替换**。
- 传输走 HTTPS，证书链与主机名按客户端已有配置校验。

## 版本号规则

版本号是点分数字（最多四段，如 `2.0.2`）。控制台按数值比较判断谁需要升级，
`2.0.10` 高于 `2.0.9`。

**发布新版本时必须同时修改客户端版本常量**，否则会陷入"升级完还提示升级"的循环：

| 文件 | 需要改的常量 |
|---|---|
| `c/client/include/fastp2p.h` | `FASTP2P_VERSION` |
| `c/client/CMakeLists.txt` | `project(fastp2p_c VERSION ...)` |

客户端登录时把 `FASTP2P_VERSION` 上报给网关，控制台正是用它和上传包的版本号比较。
如果上传的包版本写成 `2.0.2`、但构建里仍是 `2.0.1`，客户端升级后依然上报 `2.0.1`，
控制台就会一直认为它需要升级。

## 首次升级必须手动

远程升级依赖客户端认识升级指令，因此**已经在运行旧版的设备需要先手动安装一次**
本次构建（Windows 双击安装包、Android 安装 APK、Linux 覆盖可执行文件并重启服务）。
完成这一次之后，后续版本都可以从控制台远程下发。

## 回滚

- Linux / macOS 保留 `<可执行文件>.old`，可直接改回。
- Windows 替换前服务已被停止，失败时服务管理器会按既有的失败恢复策略重启旧版本。
- 网关侧的安装包与数据库元数据都在 `/var/lib/fastp2p/updates` 与 `nodes.sqlite3`，
  备份这两处即可完整回滚。
