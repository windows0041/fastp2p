# 客户端远程升级

在 Web 控制台把新版客户端安装包上传到网关，然后对单个节点或所有旧版本节点下发升级。
安装包保存在网关。客户端通过所连接的网关 TLS 端口下载，管理页和上传接口由独立的管理端口提供。

## 同步 GitHub 与新设备接入

在控制台的「客户端升级」中点击「同步 GitHub 最新版」。网关从配置的 GitHub 仓库挑选版本号最高的 `fastp2p-client-vX.Y.Z` 稳定版，校验 `SHA256SUMS.txt` 和 GitHub 提供的摘要，再将完整的一批安装包加入列表。同步完成后，可选择节点下发升级，或为新设备点「下载安装包」。Linux 和 macOS 的在线节点需上报架构才能匹配同步来的包。

下载的文件名包含本网关的 16 位接入 Token，请只交给可信设备。Windows 双击 `.exe`。新版网关为 Linux 生成自包含安装脚本，执行 `sh fastp2p-<16位Token>`（也可用 Bash），非 root 时自动请求 sudo。macOS 用当前账号执行。安装器从文件名读取 Token，用包内预置的地址和 CA 验证网关。Linux 脚本中不写入 Token，共享缓存也不保存 Token；不要重命名丢失 Token。历史 Release 里的旧安装器仍按其原有方式接入。

同步完整且校验成功后，网关自动删除所有较低版本的缓存，包括手动上传的旧包；同版和更高版本的手动包保留。同步失败不触发清理。已下发升级或开始下载的版本保留至少十分钟，随后由后台清理重试；已经打开的下载流可继续读取。表格中的大小和 SHA256 对应原始程序，Linux 下载脚本另含安装逻辑，大小和摘要不同。

Android 下载并安装 APK 后，点控制台「客户端安装 Token」里的「安卓接入」链接。Android 安装器不会把下载文件名交给应用，链接负责传递 Token。

网关安装时将 `fastp2p-sync-releases.py` 和网关二进制放在同一目录，并确保 `/usr/bin/python3` 可用。Docker 镜像包含这两项。默认同步 `windows0041/fastp2p`，自建网关可用 `FASTP2P_RELEASE_REPOSITORY=owner/repo` 指向使用自身网关地址和 CA 构建的公开 Release。

## 使用

1. 登录网关控制台，在「客户端升级」面板点「同步 GitHub 最新版」或「上传安装包」。
2. 手动上传时选择平台（Windows / Linux / Android / macOS）、填写版本号（如 `2.0.2`）、选择文件。
3. 上传后，节点列表里版本较旧的在线节点会出现「升级到 2.0.2」按钮；也可以点
   「升级所有旧版本」一次性下发。

节点在线时立即执行；离线节点不会收到指令，下次上线后仍需再次下发（升级指令不排队）。

控制台在下发后显示「等待客户端重启并上报新版本」，收到目标版本后才显示升级完成。六分钟仍未收到新版本时，会提示检查日志或手动安装。批量升级会列出未下发的节点及原因；旧 Linux/macOS 客户端未上报架构时，需要先手动安装一次适合该架构的新版。此进度保存在当前页面中，重新打开页面后请以节点上报版本为准。

Windows 客户端 2.0.3 修复了服务报告停止后 EXE 仍短暂被占用、导致替换失败又启动旧版的问题。升级助手会等待文件释放后重试替换，新服务启动失败时仍恢复旧程序。

## 各平台的行为

| 平台 | 行为 | 是否需要人工确认 |
|---|---|---|
| Windows | 下载校验后，新版本从临时目录启动一个助手：等旧服务停止、替换 `C:\Program Files\fastp2p\fastp2p.exe`、再启动服务 | 否 |
| Linux | 新安装器的服务在 `/usr/local/fastp2p/bin` 中替换程序并重新执行，保活仍由 systemd/procd/OpenRC 管理 | 否 |
| macOS | 同 Linux（launchd 不受影响） | 否 |
| Android | 下载校验后弹出通知，点按通知进入前台界面交给系统安装器 | **是**，手机上必须点通知并确认安装 |

## 安全模型

- 上传接口需要控制台登录凭据（JWT）。
- 下载接口需要网关的 16 位安装 Token，与客户端登录用的是同一个密钥。
- 客户端按网关下发的 SHA256 校验安装包，**校验不通过绝不替换**。
- 网关检查文件格式。桌面客户端在替换前试运行安装包的 `--version`，拒绝无法执行或无法识别为 fastp2p 的包。
- 传输走 HTTPS，证书链与主机名按客户端已有配置校验。

## Android 的额外前提

当前 Android 客户端通过通知请求安装，不直接从后台服务弹出系统安装器。系统是否需要用户确认，取决于系统版本、安装来源和设备管理权限。因此控制台下发后，手机端流程是：

1. 客户端下载并校验安装包（失败即止，不触碰现有应用）；
2. 弹出一条「fastp2p 有新版本」通知；
3. 用户点通知，前台界面把包交给系统安装器。系统需要确认时，点按「确认 fastp2p 升级」通知进入系统确认框。

还需要在系统设置里为本应用打开「安装未知应用」（首次点通知时会自动跳到该开关）。
不打开时安装器会直接拒绝。

## 版本号规则

版本号是点分数字（最多四段，如 `2.0.2`）。控制台按数值比较判断谁需要升级，
`2.0.10` 高于 `2.0.9`。

**发布新版本时必须同时修改客户端版本常量**，否则会陷入"升级完还提示升级"的循环：

| 文件 | 需要改的常量 |
|---|---|
| `c/client/include/fastp2p.h` | `FASTP2P_VERSION` |
| `c/client/CMakeLists.txt` | `project(fastp2p_c VERSION ...)` |
| `c/client/android/app/build.gradle` | `versionCode`（必须递增）与 `versionName` |

客户端登录时把 `FASTP2P_VERSION` 上报给网关，控制台正是用它和上传包的版本号比较。
如果上传的包版本写成 `2.0.2`、但构建里仍是 `2.0.1`，客户端升级后依然上报 `2.0.1`，
控制台就会一直认为它需要升级。

Android 还额外要求 APK 的 `versionCode` **严格大于**已安装版本：同版本或更低会被系统
直接拒绝且没有任何提示。客户端会先比较，发现不是更高版本就写日志跳过。

## 首次升级必须手动

远程升级依赖客户端认识升级指令，因此**已经在运行旧版的设备需要先手动安装一次**
本次构建（Windows 双击安装包、Android 安装 APK、Linux 执行控制台下载的脚本）。
完成这一次之后，后续版本都可以从控制台远程下发。

旧 Linux 服务使用安装脚本迁移到 `/usr/local/fastp2p`，自动移除旧 `20-remote-upgrade.conf` 路径覆盖，保留配置和 DeviceID。新安装器的 root 控制脚本放在根用户持有的目录中，服务仅能写 `bin` 和 `state`；`/usr/local/bin/fastp2p` 是单独的 CLI 副本，更新后运行服务的版本以控制台上报为准。自定义服务单元需自行确认权限与更新路径。Windows 的远程替换由 fastp2p 系统服务执行。

## 回滚

- Linux / macOS 保留 `<可执行文件>.old`。系统拒绝执行新程序时，更新器会恢复并重新执行旧程序。
- Windows 替换前保留旧程序。新服务启动失败时，更新助手尝试恢复旧程序并启动服务。
- 网关侧的安装包与数据库元数据都在 `/var/lib/fastp2p/updates` 与 `nodes.sqlite3`，
  备份这两处即可完整回滚。
