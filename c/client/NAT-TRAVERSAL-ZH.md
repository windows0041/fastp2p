# NAT 类型检测与打洞策略（借鉴 EasyTier）

本文记录对 [EasyTier](https://github.com/EasyTier/EasyTier) 的阅读结论（commit `24e0303`），以及 fastp2p 当前的差距和改造建议。EasyTier 为 Rust 实现，涉及文件：

| 文件 | 作用 |
| --- | --- |
| `easytier-core/src/connectivity/stun/client.rs` | NAT 类型判定（`UdpNatTypeDetector`） |
| `easytier-core/src/connectivity/hole_punch/udp/common.rs` | NAT 归类与「方法矩阵」 |
| `easytier-core/src/connectivity/hole_punch/udp/client.rs` | 主动方打洞流程 |
| `easytier-core/src/connectivity/hole_punch/udp/server.rs` | 被动方按指令发打洞包 |
| `easytier-core/src/connectivity/hole_punch/udp/socket_array.rs` | 多本地端口阵列（对称 NAT 用） |

## 一、NAT 类型判定

### 1.1 类型集合

EasyTier 用 9 个值，实际判定路径只会产出其中 7 个：

| 值 | 含义 |
| --- | --- |
| `OpenInternet` | 公网直连，映射地址等于本地地址 |
| `NoPat` | 有 NAT 但不改端口 |
| `FullCone` | 完全锥形 |
| `Restricted` | IP 受限锥形 |
| `PortRestricted` | IP+端口受限锥形 |
| `SymmetricEasyInc` / `SymmetricEasyDec` | 对称 NAT，但映射端口可预测（递增/递减） |
| `Symmetric` | 对称 NAT，端口随机 |
| `Unknown` | 探测不足 |

### 1.2 判定算法（UDP，`nat_type_udp`）

从**同一个本地套接字**向多个 STUN 服务器发请求，收集每个服务器看到的映射地址：

1. **少于 2 个服务器应答** → `Unknown`，不做结论。
2. **锥形判定**：所有服务器报告的映射地址完全相同 → 端点无关映射（cone）。
   - 若某个服务器从**不同 IP** 回包被收到（`has_ip_changed_resp`）：说明 NAT 放行了未通信过的源地址
     - 映射 IP 是公网且端口未改 → `OpenInternet`
     - 端口未改但 IP 变 → `NoPat`
     - 否则 → `FullCone`
   - 否则若某个服务器从**同 IP 不同端口**回包被收到（`has_port_changed_resp`）→ `Restricted`
   - 否则 → `PortRestricted`
3. **对称判定**：不同服务器看到不同映射地址。
   - 公网 IP 多于 1 个、可用应答 ≤ 1、或映射端口跨度 > 15 → 直接判 `Symmetric`
   - 否则做**额外绑定测试**：另绑一个本地端口取映射端口
     - 新端口比此前最大端口大且差值 < 100 → `SymmetricEasyInc`
     - 新端口比此前最小端口小且差值 < 100 → `SymmetricEasyDec`
     - 否则 → `Symmetric`
4. 判定完成后 10 分钟重测一次；未判定成功则 10 秒后重试。

对应常见中文编号（README 提到 NAT4-NAT4）：NAT1 ≈ Open/NoPat/FullCone，NAT2 ≈ Restricted，NAT3 ≈ PortRestricted，NAT4 ≈ Symmetric。

## 二、打洞方法矩阵

`UdpNatType::get_punch_hole_method(self, other)` 决定由**谁当主动方**：

| 本端 \ 对端 | Cone | EasySym | HardSym | Unknown |
| --- | --- | --- | --- | --- |
| **Cone** | ConeToCone | 不可（对方主动） | 不可 | ConeToCone |
| **EasySym** | SymToCone | EasySymToEasySym | 不可 | SymToCone |
| **HardSym** | SymToCone | 不可 | 不可 | SymToCone |
| **Unknown** | ConeToCone | 不可 | 不可 | ConeToCone |

要点：

- **对称方永远主动**（`can_punch_hole_as_client` 只有在 `self.is_sym()` 或双方都是 EasySym 时才为真）。
- 双方都是锥形（含 NAT2-2、NAT2-3、NAT3-3）统一走 **ConeToCone**，不区分受限级别。
- 双方都是 EasySym 时，**PeerId 小的一方**当主动方，避免双向同时发起。
- HardSym 对 HardSym 返回不可行；README 宣称的 NAT4-NAT4 依赖下面第三节的「端口阵列 + 随机喷洒」概率命中。

## 三、四类执行流程

### 3.1 ConeToCone（覆盖 NAT2-2 / NAT2-3 / NAT3-3）

1. 主动方向对端（经信令）请求**打开/复用打洞监听器**，拿到对端的映射地址。
2. 主动方绑定打洞套接字，用 STUN 得到自己的映射地址。
3. 立刻向对端映射地址发一个打洞包。
4. 通过信令让对端向**自己的映射地址**发打洞包：`packet_count_per_batch=2`、`packet_batch_count=5`、`packet_interval_ms=400`（即 5 轮、每轮 2 个、间隔 400ms）。
5. 主动方 `connect()` 重试 2 次，每次循环每 200ms 补发一个打洞包，直到握手成功。

本质就是**双方同时向对方映射地址发包**，把两侧 NAT 的过滤表同时打开。fastp2p 现有的 `punchts` 同步机制属于这一类，但没有「对端按批次补发」这一步。

### 3.2 SymToCone（覆盖 NAT2-4 / NAT3-4）

主动方是对称侧，流程同上，差别在于对称侧的映射端口每次都变，所以它需要**让对端往一批预测端口上喷洒**：

- 若对称侧是 EasySym：RPC `SendPunchPacketEasySym{base_port_num, max_port_num=50, is_incremental}`；
  对端按方向枚举 `base+1..base+50` 或 `base-1..base-50` 全部发一遍。
- 对端若也是 EasySym 并且要主动打我们，会额外做 `apply_peer_easy_sym_port_offset(base, inc)`，即故意偏移 ±20 个端口，避免双方预测到同一段。

### 3.3 EasySymToEasySym

PeerId 小的一方当主动方；双方都预测对端端口窗口（±50 枚举），主动方偏移 20 保证覆盖不同区间。

### 3.4 HardSym 的随机喷洒（NAT4 相关）

被动侧持有 **1..65535 的全局打乱端口表**（`shuffled_port_vec`），每次 RPC `SendPunchPacketHardSym{round, port_index}`：

- 第 1 轮随机取 600~800 个端口，各发一个打洞包，做 2 遍；
- 轮次越多，窗口越小：`max_k2 = (max_k2 * 2 / round).max(180)`；
- 返回 `next_port_index` 作为下一轮的游标。

主动侧则维护一个**本地端口阵列**（`UdpSocketArray`，可配置上限），从所有本地端口同时向对端映射地址发包，然后用 `try_fetch_punched_socket(tid)` 看哪个本地端口收到了回包——哪个通了就用哪个连接。这就是「N×M 生日碰撞」，用端口数量换成功率。

## 四、fastp2p 的差距

| 能力 | EasyTier | fastp2p 现状 |
| --- | --- | --- |
| NAT 分类 | 7 种（含 cone 细分与 EasyInc/Dec） | 二值：`nat_port == local_port ? 1 : 2`，失败记 314 |
| 判定依据 | 多 STUN 服务器比对映射 + 额外绑定测试 | 单一 STUN 映射与本地端口比较 |
| 锥形对锥形 | 双方同时发 + 对端按批次补发 | 有时间同步的同时发起，无补发 |
| 对称对锥形 | 预测端口窗口（±50）让对端喷洒 | 无，直接判失败转中继 |
| 双 EasySym | 低 PeerId 主动 + 偏移 20 | 无 |
| 对称 NAT | 本地端口阵列 + 随机喷洒 | 无 |
| 中继回退 | 有 | 有（本次已加排序与手动指定） |

也就是说：**NAT2-2、NAT2-3、NAT3-3 这三类 fastp2p 理论上已能打通**（都属于同时发起的锥形对锥形），失败多与「只有一次同步发包、没有补发窗口」有关；而 **NAT2-4 / NAT3-4 以及 HardSym 组合 fastp2p 完全没有实现**，只能落到中继。

## 五、fastp2p 已实现的分类（第 1 步）

`nattype` 字段（登录查询串、`7/1` 与打洞协商回包）取值：

| 值 | 含义 | 判定方式 |
| --- | --- | --- |
| 1 | Cone | 同一本地套接字对两个目的端口得到**相同**映射端口 |
| 3 | EasySym-递增 | 映射随目的变化，且换本地端口后新映射比原映射大 1~100 |
| 4 | EasySym-递减 | 同上，但比原映射小 1~100 |
| 2 | HardSym | 映射随目的变化且步长超出 ±100，或第二端口探测失败 |
| 314 | Unknown | 探测超时 |

实现位置：`client.c` 的 `tick_nat` 三阶段探测与 `nat_classify`。中继候选过滤只接受
`1`（以及未知），`2/3/4` 一律不作为中继——它们都无法接受陌生来源的入向包。

## 六、已落地的四项改造

| 步骤 | 内容 | 状态 |
| --- | --- | --- |
| 1 | 三阶段 NAT 探测与分类（cone / EasySym± / HardSym） | 已完成，单测 `nat-classify` 覆盖 |
| 2 | 打洞开局 50ms 密集补发，半秒后回到 200ms | 已完成，单测覆盖节奏 |
| 3 | 对称侧在打洞回复中公布预测窗口（≤50 端口），对端开局喷洒一次 | 已完成，单测覆盖窗口规划 |
| 4 | 任一侧 HardSym 时只打 1 轮即升级中继 | 已完成，单测覆盖梯次预算 |

### 第 4 步为何没做端口阵列

EasyTier 对 HardSym 使用「N×N 本地端口阵列」：双方各开多个本地 socket 同时发包，
靠数量撞中一对映射。fastp2p 的 QUIC 上下文绑定在单个 UDP socket 上（`opq_new` 之后
无法迁移连接），要做端口阵列必须让 QUIC 支持跨 socket 迁移，代价远高于收益。
因此 HardSym 场景改为**更快地走中继**：把两轮打洞（各 10 秒）压成一轮，
用户可感知的等待时间减半，且中继排序与手动指定已经能选到 NAT 条件好的节点。

### 窗口喷洒的集成覆盖

真机缺少 NAT 2 节点时，用 `FASTP2P_NAT_TYPE` 诊断开关让对端「声称」自己是
EasySym，从而把「公布窗口 → 对端记录 → 喷洒 → 建连」整条路径跑通。
`check-nat-window.sh` 会跑两种模式：

| 模式 | 期望 |
| --- | --- |
| 对端声称 NAT 3（递增对称） | 会话建成、流量通过、无认证失败 |
| 对端声称 NAT 1（锥形，对照组） | 同样建成，证明新增字段与密集发包没有破坏原有打洞 |

该开关只影响探测完成后的分类值，不改变任何线上行为；CI 的 linux 作业每次构建都会跑。

### 本机 NAT 的真实测量（2026-11-03）

用客户端同款探测（**同一个 socket** 先后打网关 27180/27181）实测：

| 位置 | 27180 映射 | 27181 映射 | 结论 |
| --- | --- | --- | --- |
| 本机（家宽） | 26771 | 26771 | 端点无关映射 → cone |
| 本机（家宽） | 26868 | 26869 | 每次新 socket 的本地端口不同，**不是** NAT 行为 |

第二行是个容易踩的坑：如果探测时每个目的地址都新建 socket，看到的"不同映射端口"
只是本地临时端口在变，会把它误判成对称 NAT。客户端从 phase 1 到 phase 2 复用同一个
socket，所以量到的是真实的映射行为——本机确实是 cone，与网关上 `natType=1` 一致。

WSL 里用 netns + iptables SNAT 复刻对称 NAT 的尝试没有成功：按目的端口改写源端口后，
回包落在宿主而不是命名空间里，需要额外的回程路由。这条路的成本高于收益，真机对称 NAT
仍等那台蜂窝手机。

### 尝试过的对称 NAT 复刻方案

| 方案 | 结果 |
| --- | --- |
| netns + iptables SNAT（按目的端口改写源端口） | 回包落在宿主而非命名空间，需要额外回程路由，未成 |
| 用户态 UDP 代理（每个包换一个新源端口） | 代理本身正确（同一 socket 两个目的端口的映射确实不同），但客户端的探测端口写死 27180/27181，流量不会经过代理 |

第二条路的结论：要让客户端的探测经过代理，得把探测端口也变成可配置，那是为测试改生产代码；
而分类已经可以用 `FASTP2P_NAT_TYPE` 直接指定，集成测试也已覆盖。因此不再继续投入。

### 手机蜂窝网络无法进行 TLS 握手（2026-11-03 实测）

安卓 M2012K10C 在蜂窝网络下表现为：

| 检查 | 结果 |
| --- | --- |
| DNS 解析 `fastp2p.top` | 正常，139.199.4.226 |
| TCP 连接 139.199.4.226:27183 | 正常（`nc` 返回 0） |
| TLS 握手 | **被重置**：`curl 35: Recv failure: Connection reset by peer` |
| 换 APN（10.127.66.165 → 10.99.26.59 → 10.29.43.153） | 同样被重置 |
| 同一客户端从 WSL / xrwmaster 连接 | 正常，`Verify return code: 0` |

结论：该运营商对非标准端口（27183）的 TLS 握手做了重置，TCP 层放行而 TLS 层阻断。
这不是客户端或网关的缺陷——同一个二进制文件在其他网络下工作正常。

同一台手机在 WiFi 下则受另一层干扰：路由器 DNS 把 `fastp2p.top` 解析到 `198.18.4.15`
代理虚拟 IP，导致证书校验失败。两个网络环境都无法完成握手。

#### 已实测 443 并不能解决，原因更正

网关现在同时监听 443 与 27183（`--altwss 443`，见下节）。实测结果：

| 来源 | 27183 | 443 |
| --- | --- | --- |
| 服务器本机回环 | 握手成功 | 握手成功 |
| WSL（家宽） | 握手成功，客户端认证通过 | 被重置 |
| 手机（蜂窝） | 被重置 | 被重置 |

所以**不是按端口阻断**：服务器两侧都正常，两条外部路径各自有不同的干扰。
原先「运营商封锁非标准端口」的推断已被这组数据否定。

换用中国电信卡后（`10.25.60.99`，ccmni1）结果相同：27183 与 443 都被重置。
服务器侧 `ss -tn` 只看到 27183 上的既有客户端，没有来自手机的任何已建立连接，
说明握手在到达网关之前就被终止。

同时排除了本机干扰：手机没有 VPN（`always_on_vpn_app` 为空，网络标记为 `NOT_VPN`），
也没有 Clash / sing-box 一类代理应用。两台不同运营商的蜂窝网络表现一致。

换回 27183 后**同一张卡立刻认证成功**（`gateway authenticated`，上报 `natType=1`，
公网 `183.42.243.157`）。所以先前「两条蜂窝路径都无法握手」的结论是错的，
真实情况是：

| 网络 | 27183 | 443 |
| --- | --- | --- |
| 移动卡（蜂窝） | 被重置 | 被重置 |
| 电信卡（蜂窝） | **正常** | 被重置 |
| WSL（家宽） | 正常 | 被重置 |
| 服务器回环 | 正常 | 正常 |

443 只在本机回环可用，从任何外部路径都被重置。国内云主机对 80/443 通常要求域名备案，
未备案的域名/IP 会被拦，这与观察一致。

### 窗口喷洒在真实互联网上的数据面验证

`check-nat-window.sh` 在回环上验证过，但真机一直缺对称 NAT。用 `FASTP2P_NAT_TYPE`
让 `gzvps105`（公网 `134.175.48.57`）上的一个临时客户端声称自己是 EasySym，
与 `xrwmaster` 走真实公网配对：

```
{"event":"state","state":2,"message":"gateway authenticated"}
{"event":"tunnel","state":2,"message":"QUIC tunnel connected"}      ← 直连，没有中继
{"event":"forward","state":2,"message":"forward attached to tunnel"}
读到对端 banner：SSH-2.0-OpenSSH_9.2p1 Debian-2+deb12u10
```

这条证明了「公布窗口 → 对端记录 → 喷洒 → 直连 → 数据流动」整条链路在真实网络上可用，
且不需要中继兜底。它不证明喷洒能救回一个真正的对称 NAT（那需要真机），只证明这条路
不会破坏本来能通的场景——与集成测试的结论一致，但这次是真实公网。

### 拦截是按目的地址，不是按端口（2026-11-03 对照实验）

用香港主机 `xrwhk`（`85.189.40.130`）做对照，同样在 443 上起监听：

| 从手机（移动卡）连到 | 结果 |
| --- | --- |
| `139.199.4.226:27183`（大陆网关） | TCP 通，TLS 被重置 |
| `139.199.4.226:443`（大陆网关） | 连 TCP 都被拒 |
| `85.189.40.130:443`（香港主机） | **正常，收到响应** |

所以问题不在端口，也不在运营商一刀切，而是**到这台大陆服务器的路径被拦**。
香港主机从同一张卡可以正常访问。

这也解释了为什么换运营商（移动 / 电信）表现不同：两条路径被拦的程度不一样。

结论：手机类客户端要稳定接入，网关需要放在境外或做境外前置。
这属于部署架构调整，需要单独确认。

因此客户端预设端口保持 **27183**；`--altwss` 保留为可选能力，供确实能走 443 的网络使用，
但**不要**把它当作默认。

### NAT2-4 真机验证的阻塞状态

唯一 NAT 2 节点是安卓 M2012K10C（蜂窝，公网 `223.104.76.124`）。该设备：

- USB 已断开，`adb devices` 为空，无线 ADB 也无法连接；
- 网关侧 `lastSeen` 已停止更新，即已离线；
- 且仍运行旧构建，未装上新客户端。

因此窗口喷洒的**真机数据面**暂无法验证。等待该设备重新插上 USB（或开启无线调试）
并装入新 APK 后，按下面的顺序补验：

1. 登录时观察网关节点列表的 `natType`：变成 3/4 说明新分类生效，仍是 2 说明它是
   真正的 HardSym（那么按设计走 1 轮打洞后中继，也是正确行为）；
2. 推一条规则到该手机，目标选 xrwmaster（NAT 1），从手机本地端口取数据；
3. 若直连成功 → 窗口喷洒生效；若失败 → 应在 1 轮打洞后进入中继，等待时间比旧构建减半。

### 四类组合的现状

| 组合 | 结果 |
| --- | --- |
| NAT2-2 / NAT2-3 / NAT3-3（双方锥形） | 双向同时发包 + 开局密集补发，应可直连 |
| NAT2-4 / NAT3-4（一侧 EasySym） | 对称侧公布窗口，对端开局喷洒 ≤50 个端口 |
| NAT4-4 / 任一侧 HardSym | 1 轮打洞后升级中继（排序优先 NAT 1、非对端同公网地址） |
| 双方都是 HardSym 且有第三节点 | 网关自动选优；也可用 `RelayNode` 指定 |

## 七、后续可做

1. **把二值分类换成 EasyTier 的判定**：多 STUN 服务器比对映射地址 → cone/对称；再用「另绑一个端口看映射端口差」判 EasyInc/Dec。这一步只改探测，不改协议，风险最低。
2. **锥形对锥形加补发窗口**：协商时让对方在 2 秒内每 400ms 补发一次（共 5 轮），而不是只发一次。可直接复用现有 gateway 的 `main 3 sub 1/2` 打洞协商，增加 `count/interval` 字段。
3. **对称侧预测端口窗口**：对称侧把「自己下一次映射可能落在的区间」和方向告诉对端，对端在 `base±50` 上喷洒。fastp2p 已有 `main 3 sub 2` 回包可承载这些字段。
4. **本地端口阵列**：为对称 NAT 场景预留 N（建议 8~16）个打洞套接字，哪个先收到回包就用哪个。注意 fastp2p 是单线程事件循环，端口阵列要纳入 `step()` 的 fd 集合。
5. 协议字段扩展需要同步升级 `fastp2p2` 的协商消息，网关侧无需改动（打洞包走端点直连）。

以上 2~4 项会改变打洞协商的字段，属于协议演进；建议先做第 1 项（纯探测）并补一个「我方 NAT 类型 + 对端 NAT 类型 → 是否值得尝试打洞」的决策表，让中继回退更快，再视需要在下一版协议里加喷洒能力。
